## TL;DR

Today the learning loop is manual: the `incident-postmortem` skill calls itself "raw material for
the learning loop" and only the explicit `learn from TICKET-123` HIL command (SIO-1126 lane) feeds
durable memory. Nothing guarantees a postmortem or the wiki/memory-PR chain runs when an incident
is closed. Goal: on incident closure, deterministically execute
incident-postmortem -> wiki-ingest -> memory-pr as a background skillflow run — never inside the
SSE/interrupt path, failure-tolerant (a failed chain must not affect the user-facing turn), and
propose-only (memory-pr opens a PR: agent proposes, GitOps disposes).

## Context — how this ticket came to be

During the 2026-08-01 preset-workflows session the user asked "how we close an instance and the
learnings should be consistent" — pointing at the gap between the shipped postmortem skill
(SIO-1347, PR #569) and the manual-only learn command. The root agent's
`agents/incident-analyzer/workflows/incident-triage.yaml` ALREADY declares the post-chain
declaratively (see below); it has simply never had a runtime executor.

## Where the bodies are buried

- **The declarative chain already exists**: `agents/incident-analyzer/workflows/incident-triage.yaml:34-53`
  ```yaml
  - name: post_wiki
    skill: wiki-ingest
    ...
  - name: learn
    tool: memory-pr
    depends_on: [post_wiki]
    with:
      proposal: ${{ steps.post_wiki.outputs.proposal }}

  ```
  It models the whole analysis graph as one `graph: true` step and the learning chain as post
  steps. This ticket executes (a subset/extension of) those post steps, NOT the graph step.
- **Postmortem skill**: `agents/incident-analyzer/skills/incident-postmortem/SKILL.md` (SIO-1347) —
  blameless timeline/five-whys/actions; explicitly a proposal for human review.
- **Executor + handler seams to reuse**: `packages/skillflow/src/executor.ts` (`runWorkflow`),
  `packages/agent/src/resolve-identifiers-workflow-handlers.ts` (pattern for injected handlers;
  note it is resolve-identifiers-specific — build a sibling module, do not bolt onto it). The
  executor has `tool`/`node`/`skill`/`agent`/`graph` step kinds; **no `skill` handler exists
  anywhere yet** — that is the new machinery this ticket must design (a skill step = an LLM call
  with the skill body + turn context; see design questions).
- **Where "a turn completed" is known**: the four completion points that call `pruneThreadState`
  in `apps/web/src/lib/server/agent.ts` / routes (`/api/agent/stream`, `iac/resume`,
  `topic-shift`, `learning/resume`) — the stream route's completion is the natural post-turn hook
  for a background run (fire-and-forget after the response closes, mirroring how pruning is
  best-effort).
- **memory-pr tool seams** (SIO-1346, PR #568): `packages/memory-pr` — `getFileContent`/`addLabels`
  + `_setMemoryPrClientForTesting` test seam.
- **HIL learn lane (must stay unchanged)**: 6-node lane off `classify` (SIO-1126), flag
  `HIL_LEARNING_ENABLED` — this ticket complements it, never replaces it.

## The fix (step-by-step, design-first)

1. **Design the closure trigger** (needs a user decision — AskUserQuestion early): candidates are
   (a) an explicit `close incident` user command routed in `classify` like the learn command,
   (b) a FeedbackBar "resolved" signal from the web UI, (c) mitigation-accepted. Start with (a):
   cheapest, explicit, testable; leave (b)/(c) as follow-ups.
2. **New workflow artifact** `agents/incident-analyzer/workflows/incident-close.yaml`:
   steps `postmortem` (skill: incident-postmortem) -> `post_wiki` (skill: wiki-ingest, with
   report from postmortem) -> `learn` (tool: memory-pr, `error_handling: continue`),
   workflow `error_handling: best_effort`. The dry-run CI gate from SIO-1352 validates it
   automatically.
3. **Skill-step handler** (the new machinery): a `skill` StepHandler that loads the named skill's
   SKILL.md body (via `skillFilePath`/loadAgent), composes it with the closing incident's context
   (final report, findings, confidence from the completed turn's checkpointed state), makes ONE
   LLM call (production path via `@langchain/aws` — memory: probe the production path, never raw
   SDK), and returns the text as the step's declared output. Token-bound it; PII-redact via the
   existing live-memory redaction before anything persists.
4. **Background runner**: after the stream route's completion point, when the turn was a closure,
   fire `runWorkflow(incidentClose, handlers)` detached (void promise + logged errors; never
   awaited by the response). Gate with `CLOSURE_LEARNING_ENABLED` (default OFF until live-verified).
5. **Tests**: unit (skill handler composes + returns output; runner fires only on closure; failure
   never rejects the turn), plus the workflow through the executor with stub handlers; dry-run
   gate covers the YAML shape.

## Risks and edge cases

| Risk | Likelihood | Mitigation |
|---|---|---|
| Skill-step LLM call quality/cost on every closure | Medium | Explicit closure command only (no auto-trigger) + flag default OFF |
| Duplicate PRs on repeated closure of the same incident | Medium | Idempotency key (thread/ticket) checked before memory-pr step |
| Background run outliving process shutdown | Low | Best-effort by design; log-and-drop, mirror write-behind queue teardown (SIO-938) |
| Breaking the HIL learn lane | Low | Zero changes to the lane; add a regression test that `learn from TICKET-123` still routes |

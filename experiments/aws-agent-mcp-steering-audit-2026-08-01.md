## Class 1: Timeout races across a multi-target fan-out

Grepped every `Promise.allSettled` / `withTimeout` combination across `packages/agent/src/*.ts` and `packages/mcp-server-aws/src/**/*.ts`.

- `packages/agent/src/resolve-identifiers.ts` `probeAws()`: **already fixed** (SIO-1326, this same PR #559). Each estate branch inside `Promise.allSettled(estates.map(...))` has its own `withTimeout(..., awsTimeoutMs)`; the outer `safeProbe` wrap was removed in the CodeRabbit follow-up (`catchOnlyProbe` now used instead, since the per-branch timeout is already sufficient and a second outer clock could race the same failure mode through a different door -- see the code comment at `resolve-identifiers.ts:422-430`). Confirmed via direct code read; not re-tested here since it already has its own regression test and live verification in the elastic-agent PR.
- `packages/agent/src/aws-estate-router.ts`: no `Promise.allSettled` at all. It classifies which estate(s) a prompt targets (LLM router + UI-selection precedence) but does not itself fan out per-estate work -- the actual per-estate dispatch happens via LangGraph `Send`, one sub-agent invocation per estate, each independently orchestrated (not a single racing `Promise.allSettled`). Not the SIO-1326 shape.
- `packages/agent/src/mcp-bridge.ts`: two `Promise.allSettled` call sites (initial MCP server connect fan-out, health-poll fan-out). Both are per-*server* (not per-AWS-estate), each branch has its own independent connect/timeout logic, and there is no outer wrap racing the same clock a second time. Not the SIO-1326 shape.
- `packages/agent/src/kg-topology.ts`: **found the bug class**. `collectAwsRunsOn()` (ECS cluster/service enumeration for the background knowledge-graph topology sweep) fans out per estate via `Promise.allSettled(estates.map(collectEstate))`, but before this session's fix, no individual `collectEstate` call had a timeout of its own. The only clock bounding it was `runTopologySweep`'s `runSource("aws", "aws-mcp", collect)`, which wraps the ENTIRE `collectAwsRunsOn` call in one outer `withTimeout(collect(), sourceTimeoutMs())` (default 60s). A slow estate's ECS pagination could exceed that 60s outer budget while `Promise.allSettled` was still waiting on it, discarding every fast estate's already-collected edges too. Filed as [SIO-1330](https://linear.app/siobytes/issue/SIO-1330), fixed this session (see Fixes below). `collectElasticDependencies` (the sibling elastic collector under the same `runSource` wrapper) has the identical structural exposure -- flagged but out of scope for this AWS-focused audit; a follow-up ticket is recommended if the team wants it fixed too.
- `packages/mcp-server-aws/src/index.ts`: one `withTimeout` reference, in a boot-time validator comment, not a runtime fan-out. Not applicable.

**Verdict: one genuine finding (SIO-1330), fixed and tested this session. The live-incident-path fan-out (`resolve-identifiers.ts`) was already fixed in the prior elastic-agent PR and needed no further work for AWS.**

## Class 2: Steering gaps (field-matching / window-unit confusion)

Cross-checked every CloudWatch Logs Insights / Metrics Insights / field-discovery pattern in RULES.md against the real AWS API contracts (SDK type definitions + live probes against `eu-oit-prd`).

- **CloudWatch Logs Insights has no keyword/text field-type distinction to trip on.** Unlike Elasticsearch (where `error.exception.type` is a `keyword` field and `match_phrase`/`multi_match` silently return 0 hits against it), CloudWatch Logs Insights is schemaless free text; `filter @message like /regex/` works uniformly. Live-verified: `filter @message like /(?i)(error|exception|timeout)/` against `/ecs/fargate/catalog-prd-log-group` correctly matched real Kafka exception log lines (see ground-truth incident below). **No AWS analogue of the elastic keyword-field bug exists at the Logs Insights layer.**
- **`aws_logs_get_log_group_fields` already defends against the "guessed field name silently returns empty" trap** (SIO-1161's own design intent, confirmed by reading the tool's source comment: "Prevents the unknown-field empty-result loop: a query on a guessed field name returns zero rows with no error, which reads as 'no logs' when the field simply is not called that"). This is a stronger defense than elastic-agent had pre-SIO-1327 -- elastic had no equivalent field-discovery step before its fix.
- **`aws_cloudwatch_metrics_insights_query`'s `startRelative` defaults to `now-3h`**, structurally similar in shape to the elastic ML-anomaly skill's accidental `now-24h` bleed into log-search (SIO-1327's second finding) -- but on inspection this is **intentional and correctly scoped**, not a bug: Metrics Insights is a fleet-wide "who's hot right now" ranking tool (max 14-day lookback by AWS's own API limit), and RULES.md's own "Fleet-wide top-N triage" section correctly frames it as a discovery step to *find* the culprit resource, never as the tool used to investigate a specific past incident window. The code comment at `metrics-insights-query.ts:56-58` explicitly documents the deliberate distinction from the logs tool's `now-30d` default. No cross-skill bleed exists here because aws-agent has no separate skill files at all (unlike elastic-agent's ML-anomaly skill, which is where the accidental default leaked from).
- **`aws_logs_start_query`'s window handling is already hardened** against the SIO-1079/SIO-1091/SIO-1141 class of bugs: relative windows resolve server-side (no year-drift risk), a best-effort retention clamp exists, and RULES.md's own "MalformedQueryException recovery" section (lines 252-255) already prescribes the exact re-anchor-then-simplify sequence with correct phrasing ("could not be constructed", never "expired/absent").
- **RULES.md's `Failed`/`Timeout` status guidance (line 235) is prose-only, with no structural backing** -- this is the steering-side face of the Class 3 finding below: the RULES.md text is *correct* ("A `status` of `Running`/`Scheduled` is not an error... only re-issue on an invalid-id error or `Failed`/`Timeout` status"), but nothing in the loop-guard code reinforced or even detected that condition before this session's fix, so the correct prose was unsupported by any structural signal -- exactly the elastic-agent failure mode (correct-sounding steering that the tool layer doesn't actually make checkable).

**Verdict: no elastic-style field-type or cross-skill-window steering bug exists on the AWS side. The one related gap (Failed/Timeout status having no structural teeth) is captured under Class 3/SIO-1329, not filed separately here to avoid double-counting the same root cause.**

## Class 3: Silent partial-failure swallowing in the MCP server

Audited `packages/mcp-server-aws/src/tools/logs/*.ts` (the CloudWatch Logs Insights async lifecycle) and `packages/mcp-server-aws/src/tools/cloudwatch/*.ts` for a partial/failed/timed-out result reported as if it were clean, complete data.

- **Found the bug**: `GetQueryResultsCommandOutput.status` (verified against the `@aws-sdk/client-cloudwatch-logs` SDK's own `models_0.d.ts` type definitions, not just prose docs) can be `Cancelled | Complete | Failed | Running | Scheduled | Timeout | Unknown`. CloudWatch returns every one of these as an ordinary HTTP 200 with no thrown exception -- so the wrapper's only failure path (`mapAwsError` in a `catch` block) never runs for a `Failed`/`Timeout`/`Cancelled` query. `packages/mcp-server-aws/src/tools/logs/get-query-results.ts` passes the raw SDK response straight through `wrapListTool` with no `status` inspection at all.
- On the agent side, `packages/agent/src/sub-agent-loop-guard.ts`'s `isEmptyAwsQueryResults()` (the SIO-1159 mechanism that nudges the LLM to widen its search window after consecutive empty successes) only recognized `status === "Complete"`. A `Failed`/`Timeout`/`Cancelled` result fell through to `recordResult`'s `!isInFlightAwsQueryResults` else-branch, which **silently reset the consecutive-empty counter to 0** -- actively worse than a no-op, since it erased a genuine 0-row streak's progress toward the widen advice while emitting no signal that the query never actually completed.
- Confirmed with a standalone repro script BEFORE any fix: `isEmptyAwsQueryResults('{"status":"Failed","results":[]}')` returned `false` (correctly not double-classified as empty-success), but there was no corresponding positive detection either -- the response was invisible to every loop-guard mechanism.
- Attempted to force a live `Failed`/`Timeout`/`Cancelled` result against real AWS (`eu-oit-prd`) to observe the raw SDK response directly: a `pattern`+`diff` query over a 30-day window against `/ecs/fargate/catalog-prd-log-group` (118M+ records scanned) completed successfully rather than timing out. CloudWatch's 60-minute query timeout and genuine execution failures are not reliably forceable on demand without either waiting an hour or crafting a query that fails at execution time rather than submission time (a submission-time syntax error throws `MalformedQueryException`, which IS already handled -- the gap is specifically the *harder-to-trigger* execution-time failure class). The bug is grounded instead in the AWS SDK's own documented response contract, matching this repo's runbook precedent for tool-schema claims verified against upstream docs rather than forced live reproduction.

Filed as [SIO-1329](https://linear.app/siobytes/issue/SIO-1329), fixed this session (see Fixes below).

**Verdict: one genuine finding, same bug class and root cause shape as SIO-1328's Elasticsearch `_shards.failed` swallow (a success-shaped HTTP 200 hiding a real failure), fixed and tested.**

## CodeRabbit review (PR #560, round 1) -- 3 findings, all confirmed and fixed

1. **This doc's own verification arithmetic was wrong** (the line above, before this edit): claimed "3504 -> 3506, net +8" when the real baseline/delta didn't reconcile, and mis-stated that the SIO-1330 kg-topology test lived in "a different package" -- it does not; `kg-topology.ts`/`kg-topology.test.ts` are both under `packages/agent/src/`, same package as the other two fixes. Corrected above with the verified-precise 3499->3507 (+8) breakdown.
2. **`awsEstateTimeoutMs()` used manual `Number()` parsing instead of the repo's established Zod-validated env-reader convention.** This repo already has a shared `readPositiveIntEnv()` helper (`packages/shared/src/env-validation.ts`, added in SIO-1308 specifically to replace this exact anti-pattern repo-wide) -- I copied the *old*, superseded `kafkaDescribeTimeoutMs()`-style manual parsing instead of using it for a brand-new numeric tuning knob. Fixed: `awsEstateTimeoutMs()` now calls `readPositiveIntEnv("KG_TOPOLOGY_AWS_ESTATE_TIMEOUT_MS", AWS_ESTATE_TIMEOUT_DEFAULT_MS, logger)`. Behaviorally equivalent (both reject non-integer/non-positive/unparseable input and fall back to the default) but now matches team convention and gets a warning log on invalid input for free.
3. **`isFailedAwsQueryResults()` was missing CloudWatch's `Unknown` status.** Verified against the AWS SDK's own `GetQueryResultsResponse.status` type union (`Cancelled | Complete | Failed | Running | Scheduled | Timeout | Unknown`) -- `Unknown` is a seventh possible value I omitted from the original SIO-1329 fix, and it is exactly as untrustworthy as `Failed`/`Cancelled`/`Timeout` (not `Complete`, not `Running`/`Scheduled`), so it fell through to the same counter-reset bug the original fix existed to close. Fixed: added `"Unknown"` to `AWS_FAILED_QUERY_STATUSES`, updated `AWS_FAILED_QUERY_ADVICE`'s wording to name it, added 2 new regression tests (confirmed FAILING before this fix, PASSING after).

All three findings verified against live code/docs before fixing (per this repo's CodeRabbit-triage discipline of never applying a suggestion without independent verification) -- all three were genuine, none were declined.

## Context -- how this ticket came to be

SIO-1774 measured where the fat tool results in run `f77ce7dd` really came from and fixed each at its
source. Three of the four fixes live in MCP server code, which the agent does not load: the server
process has to run it. At the end of the session the state of those processes was checked
(read-only) and found to predate every merge of the day. This ticket exists so the rollout is a
tracked, verified act rather than something assumed to have happened.


`AWS_MCP_URL` and `KAFKA_MCP_URL` point at localhost 3001 and 3000, but those processes are only
SigV4 PROXIES: `AWS_AGENTCORE_RUNTIME_ARN` is set, so the real AWS MCP server is the AgentCore
runtime. Restarting the process on 3001 does NOT deploy SIO-1774's AWS change. Couchbase and
Atlassian have no AgentCore ARN in the env: they really are the local processes.

`--hot` means a `git pull` in the main checkout reloads the local servers on its own. Treat that as
likely, not guaranteed: verify by behaviour (section Verification), and restart if in doubt.

**The three server changes being rolled out (PR #813):**

- Couchbase, `packages/mcp-server-couchbase/src/tools/queryAnalysis/analysisQueries.ts:160`
  `completedRequestsQuery(includePlan = false)` and `:175` `COMPLETED_REQUESTS_DEFAULT_LIMIT = 20`;
  `getCompletedRequests.ts:15,38` the `includePlan` param. Was `SELECT *, meta().plan`, 745 KB for at
  most 50 rows. Now explicit fields, `ORDER BY STR_TO_DURATION(elapsedTime) DESC`, default 20, plan
  only on request, and `status: "success"` maps to the server's `completed`.
- AWS, `packages/mcp-server-aws/src/tools/cloudwatch/describe-alarms.ts:53` `omitAlarmNoise` and
  `:22` `includeNotificationConfig`. Drops `AlarmArn`, `ActionsEnabled`, `OKActions`, `AlarmActions`,
  `InsufficientDataActions`, `StateReasonData` unless asked. Was 78 KB and 118 KB. It adds a
  PARAMETER, not a tool, so the toolCount canary must stay 70.
- Atlassian, `packages/mcp-server-atlassian/src/tools/proxy/index.ts:94` `slimJqlSearchText`: caps
  each description at 4096 bytes (true UTF-8 byte cap), strips `avatarUrls` / `iconUrl` / `self` /
  `expand`, adds a `_projection` sentinel (`:118`). Was 127 KB.

Note that the fourth cause SIO-1774 found needs no rollout: `@langchain/mcp-adapters` delivering a
payload twice (text plus `structuredContent`) is fixed agent-side, in
`packages/agent/src/evidence-exec.ts` `dropDuplicateStructuredContent`.

## The rollout (step by step)

### 1. Pull main on the workstation -- USER DECISION

The main checkout has 1 uncommitted file. Look before pulling; never stash with a bare `git stash`
(the stash stack is shared across worktrees and sessions).

```bash
cd /path/to/devops-incident-analyzer          # the MAIN checkout, not a worktree
git status -s
git fetch origin && git log --oneline HEAD..origin/main | wc -l      # expect 16 or more
git pull --ff-only
bun install                                    # SIO-1776 added two pinned deps to packages/shared
```

`bun install` matters: `quickjs-emscripten-core` and `@jitl/quickjs-singlefile-cjs-release-sync`
(both pinned at 0.32.0) are new. Without them the sandbox, which is now default ON, fails to load.
The web app also needs a restart to pick up agent changes reliably; that is the user's process, so
ask, do not kill it.

### 2. Couchbase and Atlassian

After the pull, run the verification for both (below). If either still shows the OLD behaviour, the
hot reload did not take: ask the user to restart that server (they own the process), then re-verify.

### 3. AWS runtime -- PRODUCTION, needs the user's explicit go-ahead

Follow `docs/runbooks/mcp-agentcore-image-deployment.md` exactly. It is current (last validated
2026-08-07) and carries the runtime id, ECR repo, execution role and log group. The parts that have
gone wrong before, in its own words:

1. Verify the account first: `aws sts get-caller-identity --profile eu-shared-services-prd`. The
   profile stanzas are hand-pasted SSO keys and have held the wrong account's keys before.
2. Build from merged main: `./scripts/agentcore/push-to-production-ecr.sh --package mcp-server-aws
   --export-tarball --tag sio-1774`. Image must be `linux/arm64`. If the build fails at
   `bun install --frozen-lockfile` inside the container while the host is clean, suspect
   `Dockerfile.agentcore`'s hand-maintained COPY list. SIO-1776 added DEPENDENCIES to
   `packages/shared`, not a new workspace package, so the list should not need a change, but this is
   the first image build since those deps landed: watch that step.
3. Inspect before pushing; push with a descriptive tag, never `latest`. A transient ECR 403 on the
   first push is a known recurring pattern: re-login and retry once before suspecting IAM.
4. Capture `get-agent-runtime` to a file and build the update payload from it, changing ONLY
   `containerUri`. Never hand-retype `environmentVariables`. The AWS runtime is PUBLIC network mode,
   so the VPC `networkModeConfig` gotcha (kafka only) does not apply.
5. Apply, poll to READY, then diff the new config against the captured one: only `containerUri` plus
   version, timestamps and status may differ.
6. Record the PREVIOUS digest before you start. Rollback is editing `containerUri` back to it.

Kafka is NOT part of this rollout: SIO-1774 did not touch `mcp-server-kafka`. Do not redeploy it
"while you are there". (It does share `packages/shared`, so a future kafka deploy will carry the
day's shared changes; that is a separate decision.)

### 4. Append the deploy to the runbook's "Lessons learned"

The runbook keeps a dated entry per deploy with the new live digest and the confirmed toolCount. Add
one. That is a docs change on a branch with a PR, like any other.

## Verification

There is no documented raw `tools/call` recipe in this repo. What was run successfully during the
session is a short Bun script through the project's own MCP client, which exercises the same adapter
path the agent uses. Create it as a TEMPORARY file, run it, delete it:

```ts
// packages/agent/src/eval/_sio1786-probe.ts   (temporary; delete after use)
import { createMcpClient, getToolsForDataSource, withAwsEstate } from "../mcp-bridge.ts";
import { buildEvalMcpConfig } from "./run-function.ts";

await createMcpClient(buildEvalMcpConfig());
const call = async (ds: string, name: string, args: Record<string, unknown>, estate?: string) => {
	const tool = getToolsForDataSource(ds).find((t) => t.name === name);
	if (!tool) throw new Error(`tool missing: ${name}`);
	const run = () => tool.invoke({ id: "p1", name, args, type: "tool_call" });
	const result = (await (estate ? withAwsEstate(estate, run) : run())) as { content?: unknown };
	const content = result?.content ?? result;
	return typeof content === "string" ? content : JSON.stringify(content);
};
const report = (label: string, text: string, absent: string[], present: string[]) =>
	console.log(label, "bytes", Buffer.byteLength(text), "| must be absent:", absent.filter((k) => text.includes(k)), "| must be present, missing:", present.filter((k) => !text.includes(k)));

report("couchbase", await call("couchbase", "capella_get_completed_requests", {}), ['"plan"'], ["elapsedTime"]);
report("aws", await call("aws", "aws_cloudwatch_describe_alarms", { StateValue: "ALARM" }, "eu-oit-prd"), ["AlarmArn", "AlarmActions", "StateReasonData"], ["AlarmName"]);
// Atlassian: print the schema first, then call with a JQL that returns issues with long descriptions.
console.log(JSON.stringify(getToolsForDataSource("atlassian").find((t) => t.name === "atlassian_searchJiraIssuesUsingJql")?.schema).slice(0, 600));
process.exit(0);
```

```bash
cd packages/agent
bun --env-file=/path/to/main-checkout/.env run src/eval/_sio1786-probe.ts
rm src/eval/_sio1786-probe.ts && git status -s        # must be clean
```

From a worktree the `--env-file` MUST be the main checkout's `.env` (worktrees have none; `bun`
silently continues without it and the client connects to zero servers). AWS tools throw unless they
run inside `withAwsEstate`. Both were learned the hard way in the session. Never print the env file.

This script was run as written at 17:43 on 2026-09-17, before any rollout, so the recipe is certified
and the baseline is real, not carried over from the morning:

```

aws       bytes  78618 | must be absent: [ "AlarmArn", "AlarmActions", "StateReasonData" ] | must be present, missing: []
```

Both servers were therefore confirmed to be on pre-#813 code. After the rollout both "must be
absent" lists must be empty. The Atlassian schema printed as `jql`, `maxResults`, `fields`.

## Risks and edge cases

| Risk | Likelihood | Mitigation |
|---|---|---|
| `git pull` conflicts with the uncommitted file in the main checkout | Medium | Look first; it is the user's change and the user's call |
| Sandbox fails to load after the pull because `bun install` was skipped | Medium | Step 1 includes it; symptom is an import error for `quickjs-emscripten-core` at sub-agent start |
| `--hot` did not reload a server and the old behaviour is mistaken for a failed fix | Medium | Verify by behaviour, restart, re-verify; never conclude from the process start time alone |
| Wrong AWS account behind the profile | Low, high impact | `sts get-caller-identity` before ECR or the runtime, every time |
| Image build breaks on the new shared deps | Low to medium | First build since SIO-1776; the runbook's COPY-list diagnosis applies if `--frozen-lockfile` fails only in the container |
| Runtime config drift from a retyped payload | Low | jq-project the captured JSON; diff after the update |
| toolCount changes | Low | 70 expected; anything else means the image carries more than SIO-1774. Stop and find out before verifying further |
| A consumer depended on the dropped alarm fields or on `meta().plan` | Low | Both are opt-in parameters, not removals; the typed-finding extractors were checked in SIO-1774 and read none of them |

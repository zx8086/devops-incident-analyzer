## TL;DR

A pi verify card is suppressed for an AWS estate only when the sub-agent's ECS ledger PROVES the
focus service is absent there. After SIO-1783 the proof is no longer destroyed by a bug, but it still
only holds if the MODEL happens to list the services of every cluster in the estate. In one live
replay it listed one cluster of five, concluded "absent" in prose, and a card was proposed for an
estate the report called a confirmed negative. In the next replay it listed all five and the card was
correctly suppressed. Same code, same incident, different outcome.

The fix: after the AWS sub-agent's ReAct loop, when the only thing standing between the run and a
proof is unwalked clusters, walk them deterministically (bounded, fail-closed, soft-failing) and feed
the pages into the same ledger. Success is: replaying the incident yields exactly one verify card no
matter how thorough the model was.

## Context -- how this ticket came to be

The originating session reviewed incident run `f77ce7dd` (a PDF rendering failure in an ECS service,
two AWS estates selected, the service deployed in only one of them). Point (b) of that review was
that a "Verify with pi agent" card was proposed for the estate where the service does not exist.
SIO-1777 fixed it by adding `serviceAbsent` to the AWS result row and subtracting such estates in
`estatesFromState`. Plan: `~/.claude/plans/system-reminder-you-are-operating-hashed-locket.md`
(section B).

A full web replay later showed the card still appearing. SIO-1783 found the cause with a new
diagnostic: the model emitted `aws_ecs_list_clusters` five times in ONE turn, the four duplicate
stops latched `awsEcs.failed`, and the proof became permanently unprovable. That latch was removed
(PR #817). The first live run on the fixed code then showed what remains, which is this ticket:

```
event: subagent.aws_absence_not_proven
deploymentId: estate:eu-shared-services-prd
blockedBy: "services-incomplete:<four of the estate's five clusters>"
pi verification cards proposed  count: 2          (threadId 008d7268-4a6d-442d-9212-84273ffd83ac)
```

versus the very next replay, where the model walked every cluster:

```
event: subagent.aws_service_absent_early_exit
clustersEnumerated: 5  servicesEnumerated: 5
pi verification cards proposed  count: 1          (threadId c751d1d4-987b-4efd-afe3-800ac0ca3d27)
```

The refusal in the first case is CORRECT and fail-closed. The problem is only that the outcome is
left to model thoroughness when four cheap list calls would settle it.

  `matched`, `clusterPagesComplete`, `clusters: Set<string>` (`:401`), `servicesComplete:

- `:731` `observeEcsListResult(state, toolName, content, arg)` folds ONE list result into the

- `:702-711` a page is final only when it carries none of `nextToken`, `NextToken`, `Marker`,

- `:790` `awsEcsAbsenceProven`; `:804` `awsEcsAbsenceBlocker` (SIO-1783), quoted in full because the
  completion keys off its output:

```ts
export function awsEcsAbsenceBlocker(state: LoopGuardState): string | null {
	const e = state.awsEcs;
	if (!e.enabled) return null;
	if (e.failed) return "failed";
	if (e.matched) return "matched";
	if (!e.clusterPagesComplete) return "cluster-pages-incomplete";
	if (e.clusters.size === 0) return "zero-clusters";
	const unwalked = [...e.clusters].filter((c) => !e.servicesComplete.has(c));
	return unwalked.length > 0 ? `services-incomplete:${unwalked.join(",")}` : null;
}
```

## The fix (step by step)

### 0. The trap to avoid

SIO-1784's original text said to call the INSTRUMENTED `aws_ecs_list_services`. Do not. A cluster the
model only PARTLY paginated (page 1 fetched, page 2 never requested) is still unwalked, but
re-listing page 1 is an exact duplicate signature and `shouldShortCircuit` refuses it. The ledger
does not store the last cursor, so the walk cannot resume mid-cluster. The issue carries a dated
correction saying the same.

### 1. Add a seam so pages can reach the ledger -- `sub-agent-instrumentation.ts`

Extend the `runSignals` type and attach the function next to the `:185` seed:

```ts
runSignals?: {
	serviceAbsent: boolean;
	absenceBlockedBy?: string | null;
	// SIO-1784: folds one ECS list page fetched OUTSIDE the ReAct loop into this run's ledger.
	observeEcsPage?: (toolName: string, content: unknown, arg: unknown) => void;
};
```

```ts
if (ctx.runSignals) {
	const signals = ctx.runSignals;
	signals.absenceBlockedBy = awsEcsAbsenceBlocker(runState.loopGuard);
	signals.observeEcsPage = (toolName, content, arg) => {
		observeEcsListResult(runState.loopGuard, toolName, content, arg);
		signals.serviceAbsent = awsEcsAbsenceProven(runState.loopGuard);
		signals.absenceBlockedBy = awsEcsAbsenceBlocker(runState.loopGuard);
	};
}
```

`observeEcsListResult` is already exported from the loop guard; import it here.

### 2. The completion -- a pure, testable function, new file `aws-absence-completion.ts`

Same shape as `network-baseline.ts` (injected `invoke`, returns diagnostics):

```ts
export const MAX_COMPLETION_CLUSTERS = 10;
export const MAX_COMPLETION_PAGES_PER_CLUSTER = 5;

export interface AbsenceCompletionDeps {
	invoke: (toolName: string, args: Record<string, unknown>) => Promise<unknown>;
	observe: (toolName: string, content: unknown, arg: unknown) => void;
	blocker: () => string | null | undefined;
}

// Returns the clusters it walked. Stops the moment the blocker is anything other than
// services-incomplete: a match or a failure found on the way ends the hunt, by design.
export async function completeEcsEnumeration(deps: AbsenceCompletionDeps): Promise<string[]> { ... }
```

Rules, all of which need a test:

1. Run only when `blocker()` starts with `services-incomplete:`. Parse the cluster list from it.
   Never run for `failed`, `matched`, `zero-clusters` or `cluster-pages-incomplete`.
2. More than `MAX_COMPLETION_CLUSTERS` unwalked: do nothing. The proof stays unproven.
3. Per cluster, start from page 1 (`{ cluster }`), then `{ cluster, cursor: <nextToken> }`. Read the
   token with the same field list as `ECS_TOKEN_FIELDS`; export that constant rather than copying it.
4. Pass every page to `observe` with the SAME args used for the call: `observeEcsListResult` needs
   `cluster` from the arg or it sets `failed`.
5. After each page re-read `blocker()`. If it no longer starts with `services-incomplete:`, stop.
6. Hitting the page bound on a cluster leaves it unwalked. Do not mark anything complete by hand.

### 3. Wire it in -- `sub-agent.ts`, before the `:1999` log

```ts
if (dataSourceId === "aws" && runSignals.observeEcsPage && runSignals.absenceBlockedBy?.startsWith("services-incomplete:")) {
	const started = Date.now();
	try {
		const toolsByName = new Map(allTools.map((t) => [t.name, t]));
		const walked = await completeEcsEnumeration({
			invoke: async (toolName, args) => {
				const tool = toolsByName.get(toolName);
				if (!tool) throw new Error(`tool unavailable: ${toolName}`);
				return normalizeToolContent(await tool.invoke(args));
			},
			observe: runSignals.observeEcsPage,
			blocker: () => runSignals.absenceBlockedBy,
		});
		log.info(
			{ event: "subagent.aws_absence_completed", deploymentId, clustersWalked: walked, durationMs: Date.now() - started, provenAfter: runSignals.serviceAbsent, blockedByAfter: runSignals.absenceBlockedBy },
			"Completed the ECS enumeration the model left unfinished",
		);
	} catch (error) {
		log.warn({ deploymentId, error: error instanceof Error ? error.message : String(error) }, "ECS enumeration completion failed; continuing without it");
	}
}
```

Check what `normalizeToolContent` returns for these tools (string or parsed object) and hand
`observe` whatever `observeEcsListResult` can parse; `parseEcsListResult` accepts a string or a
text-block array. Confirm `allTools` is in scope at that point (it is used at `:2094`, which is
later in the same function).

## Risks and edge cases

| Risk | Likelihood | Mitigation |
|---|---|---|
| Completion turns a fail-closed refusal into a false "absent" | Low, high impact | Pages go through the SAME `observeEcsListResult`; nothing is marked complete by hand; a match or an error on the way sets `matched` / `failed`; both bounds leave the proof unproven |
| Extra AWS calls on every incident | Low | Only when the blocker is `services-incomplete`, bounded at 10 clusters x 5 pages; the observed case cost 4 calls |
| `normalizeToolContent` hands `observe` a shape `parseEcsListResult` cannot read | Medium | It would set `failed`, which is safe but defeats the feature; assert the shape in the harness test and in the live log |
| Completion runs but the row was already built | Low | Place the call before `:1999`, well before the `:2358` spread; the live check looks for `count: 1` |
| Estates with more than 10 clusters never benefit | Accepted | They behave exactly as today; raise the bound only with evidence |
| Non-ECS workloads (Lambda, EC2) | Known gap | Out of scope; they never set the flag, as today |

## Out of scope

- A structured absence signal for non-ECS workloads.
- Deriving `serviceAbsent` from the sub-agent's prose. SIO-1268 exists to prevent exactly that.
- Persisting the last cursor in the ledger to resume a partial walk. Re-walking from page 1 is
  simpler and the bounds cap the cost.
- Three loose ends from the originating session, none of them part of this ticket and none ticketed:
  1. `subagent.final_turn_forced` (SIO-1779) never fired in the full web replay; one correlation
     fetch hit its recursion limit with loop-guard stops through iteration 37 and ended on the
     reserved final turn instead. Covered by unit tests only. Whether `shouldForceFinalTurn`'s "three
     fully blocked rounds" is too strict when productive calls are interleaved is uninvestigated.
  2. The key-decision memory write after a pi verdict was not verified live, because the replay
     instance ran with memory off to protect the user's.
  3. The SIO-1774 result shrinking (PR #813) only takes effect once the Couchbase, AWS and Atlassian
     MCP servers are redeployed. That is a deploy action and needs the user's go-ahead.

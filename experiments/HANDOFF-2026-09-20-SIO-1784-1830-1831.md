## What shipped

### SIO-1784 -- complete the ECS enumeration (`21fe0a12`, `d20bf38e`)

`packages/agent/src/aws-absence-completion.ts` walks the clusters the model left
unpaginated, so a pi verify-card is suppressed on a *proven* absence rather than
on whatever the model happened to enumerate.

The trap, which the ticket's own original proposal got wrong and its correction
section fixes: **the completion must call the UNINSTRUMENTED tools.** The
duplicate check at `sub-agent-loop-guard.ts:857` (`seenSignatures.has(signature)`)
sits BEFORE the `RUN_BACKSTOP_EXEMPT_TOOLS` carve-out at `:862`, so re-listing
page 1 of a partly-walked cluster is refused as an exact duplicate. Pages are fed
back into the ledger through the `observeEcsPage` seam on `ctx.runSignals`
(`sub-agent-instrumentation.ts`), not through the tool proxies.

Deviation from the handover that specified this: it suggested exporting the raw
`ECS_TOKEN_FIELDS`; I exported `nextEcsToken()` instead, so the token-field
knowledge stays in one place.

Caps: `MAX_COMPLETION_CLUSTERS = 10`, `MAX_COMPLETION_PAGES_PER_CLUSTER = 5`.

### SIO-1830 -- adapt the spoke's `diagnoses` envelope (`14a679a2`, `66f2c7c3`)

A live `eu-oit-prd` spoke returned a correct, well-evidenced diagnosis under a
`{diagnoses:[...]}` envelope. Both `PiVerdictSchema` and `PiInvestigationSchema`
rejected it, and the answer was **silently discarded** behind one `warn`.

Fix is a SEPARATE schema plus adapter in `packages/shared/src/pi-coms-types.ts`
(`PiDiagnosesReplySchema`, `investigationFromDiagnoses`), tried as a third branch
in `pi-verifier.ts:583` after the existing two. Not a loosening of either existing
schema -- five malformed payloads are tested and still rejected.

Mapping worth knowing: `evidence[].command` becomes `evidence[].resource` (the
spoke records the command it ran, not an arn), `affected_resources` is *prepended*
as evidence or it would be dropped entirely, and absent `confidence` defaults to
**0.5**, never 1, so silence is not read as certainty.

Both rejection warns now log `responseKeys: Object.keys(response)`. **Keys only,
never values** -- the body carries account ids, arns and trace ids. This mattered
concretely: diagnosing the original required hand-pulling the message from the
hub, and it had **aged out within the hour** (`message_not_found` on re-fetch).

## SIO-1831 -- the open question

**Do not start this without claiming it first** (it is Todo, unassigned).

The finding that makes it actionable: `packages/pi-coms/extensions/turnReply.ts:160`
already branches on `inbound.response_schema` and already extracts JSON --

```ts
} else if (inbound.response_schema && typeof inbound.response_schema === "object") {
    const parsed = extractJsonPayload(lastAssistantText);
    if (parsed === undefined) {
        replies.push({ msg_id: inbound.msg_id, response: null, error: notJsonError(final) });
    } else {
        replies.push({ msg_id: inbound.msg_id, response: parsed, error: null });
    }
}
```

-- but it only checks the reply **is JSON**, never that it **matches the schema it
was handed**. A shape mismatch returns `error: null` and fails 90 s later at the
analyzer, where nothing can be done but log a warn.

**Why a persona-only fix is the wrong instinct here:** `coms-net.ts:813` ALREADY
injects the schema into the recipient's turn content, with a comment saying "both
account agents guessed the same wrong shape". That mechanism has already failed in
production. A third bet on it is not the recommendation; validating at the seam is.

Constraints: any change under `agents/pi-fleet/` or `packages/pi-coms/extensions/`
needs a **bundle publish + rollout** to reach spokes -- read
`packages/pi-coms/docs/deployment/deployment.md` first, never reconstruct it from
`scripts/fleet.ts`. The non-schema path must keep returning prose verbatim
(`turnReply.ts:167`). The SIO-1830 adapter **stays** either way; it is the net for
dialects not yet seen and for spokes on older bundles.

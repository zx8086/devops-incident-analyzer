### SIO-1830 -- adapt the spoke's `diagnoses` envelope (`14a679a2`, `66f2c7c3`)

A live `eu-oit-prd` spoke returned a correct, well-evidenced diagnosis under a
`{diagnoses:[...]}` envelope. Both `PiVerdictSchema` and `PiInvestigationSchema`
rejected it, and the answer was **silently discarded** behind one `warn`.

Fix is a SEPARATE schema plus adapter in `packages/shared/src/pi-coms-types.ts`
(`PiDiagnosesReplySchema`, `investigationFromDiagnoses`), tried as a third branch
in `pi-verifier.ts:583` after the existing two. Not a loosening of either existing
schema -- five malformed payloads are tested and still rejected.

Mapping worth knowing: `evidence[].command` becomes `evidence[].resource` (the
spoke records the command it ran, not an arn), `affected_resources` is *prepended*
as evidence or it would be dropped entirely, and absent `confidence` defaults to
**0.5**, never 1, so silence is not read as certainty.

Both rejection warns now log `responseKeys: Object.keys(response)`. **Keys only,
never values** -- the body carries account ids, arns and trace ids. This mattered
concretely: diagnosing the original required hand-pulling the message from the
hub, and it had **aged out within the hour** (`message_not_found` on re-fetch).

} else if (inbound.response_schema && typeof inbound.response_schema === "object") {

## SIO-1828 -- fleet inbox cannot reach a window older than the newest 100 rows

**Todo, High, unclaimed.** This is still the reason older incident windows read
empty, and it is *separate* from the SIO-1825 header-parsing bug already merged.

`fetchFleetInbox` reads each mailbox with a fixed `limit: 100` and **no cursor**
(`fleet-inbox-node.ts:63`, `MAILBOX_READ_LIMIT`), and the hub with no `since`
returns the **newest** `limit` rows (`coms-net-server.ts:634`,
`ORDER BY msg_id DESC LIMIT ?`). `withinWindow` then filters client-side over
whatever those 100 rows happen to be. So the reachable history is not a time
window at all, it is "however far back 100 messages happen to stretch", which
moves with traffic.

Measured on the live prd hub 2026-09-20: the `ops` inbox (shared by six accounts'
monitors) covers only **26.8 h** at `limit=100`, back to 2026-09-18 20:30. A run
whose window was 2026-09-16 19:10 to 2026-09-18 19:10 therefore had **zero** of its
100 rows inside the window, and would read `0` even with SIO-1825 fixed.

**The trap:** "just pass `since`" is wrong. `since` is a ULID cursor that pages
**forward** (`msg_id > ? ORDER BY msg_id ASC`), so it returns only *newer* rows.
The real fix synthesises a minimum-entropy ULID at `window.from` and pages forward
until `created_at` passes `window.to` -- a paging loop with a page cap and a
total-row cap, all inside the existing per-estate `fleetInboxTimeoutMs`. Raising
the limit is rejected: the hub caps it at 100 (`pi-coms-client.ts:522`) and it
only moves the cliff.

When a cap truncates the read the digest must say so, per the same honesty rule
SIO-1815/#846 applied to the entry cap. A silently short read is the failure mode
this ticket exists to remove.

## SIO-1829 -- verify-with-pi gets the monitor's diagnosis schema, intermittently

**Todo, High, unclaimed. Same root as SIO-1830 and SIO-1831, seen from the card.**

Same `msg_id` (`01M2Y0YER09EBRCNV4X1S5QTHH`), same `eu-oit-prd` spoke, same
`{diagnoses:[...]}` envelope. Where SIO-1830 was "the analyzer discarded a good
reply", this is the operator-visible half: the card reads
`pi agent eu-oit-prd replied with an unusable verdict (schema mismatch)`.

Two facts that shape the investigation, and neither is a formatting problem:

1. **It is intermittent, updated 2026-09-20.** A run ~50 minutes later against the
   same spoke returned a correctly-shaped `PiVerdictSchema` verdict (`confirmed`,
   five claims with evidence) and the card rendered normally. So the spoke *can*
   honour the verdict schema. That rules out "the verify path never sets
   `response_schema`" as a standing condition.
2. **The failing reply was about the wrong service.** The analyzer asked about
   `localcore-service`; the returned diagnosis was about `orders-service` /
   `ImageEventConsumer.java:36`, keyed to an orders log group. That is
   `DIAGNOSIS_RESPONSE_SCHEMA` (`monitor/report.ts:105,146`) -- the schema the
   **monitor** sends. So this reads less like bad formatting and more like a
   monitor turn's reply being delivered against the analyzer's `msg_id`.

Ruled out as a cause: the failing run executed `840a5e62`, and `f3da4d80`
(SIO-1825) is not an ancestor of it; `PiVerdictSchema` is byte-identical between
the two; the guard itself predates this work (SIO-1635, PR #682).

**Reproduction needs overlap, not repetition** -- try to run an analyzer verify
request while a monitor investigation is in flight on the same spoke, rather than
expecting failure on every call.

**Note the interaction with what shipped:** SIO-1830's adapter now accepts the
`diagnoses` envelope on the *investigation* path, so a repeat of this may surface
differently than the original "Failed" card. The `responseKeys` diagnostics added
in `66f2c7c3` are exactly what lead 3 of this ticket asked for, so the next
occurrence should be self-describing without hand-pulling from the hub. **Re-read
the failure with those diagnostics before assuming the old analysis still holds.**

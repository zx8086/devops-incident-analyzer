## TL;DR

The eval's `subagent_accuracy_<datasource>` metric floors near zero (elastic 0.019 on BOTH model legs, gitlab 0.000, couchbase ~0.12) not because sub-agents are weak or the judge is harsh, but because `buildSubagentReports` hands the judge only the typed `*Findings` objects — which are populated from a small tool subset and are usually `{}` for real investigations. The sub-agent's actual narrative report (`DataSourceResult.data`, a string) is never serialized. Fix: include `data` in the serialization alongside typed findings. Success = `subagent_accuracy_*` measures sub-agent output quality instead of serialization coverage; expect elastic to jump from ~0.02 to something commensurate with `evidence_elastic` (~0.8-0.9) on the next recorded run.

## Context — how this ticket came to be

SIO-1374 built a per-sub-agent judge to isolate the A/B variable (sub-agent model) from the constant (Sonnet 5 aggregator). From its first run, `subagent_accuracy_*` sat implausibly far below the aggregator-mediated `evidence_*` for the same incidents. SIO-1381 (2026-08-06) settled it with the SIO-1379 tool-call audit trail: for DEVOPS-1376, the sonnet elastic sub-agent made 26 elastic calls and the ground-truth phrase "Connection threshold" appears **50 times in its recorded tool results** — yet `subagentReports.elastic` serialized as `{}` and the judge correctly graded "missing". Classification: measurement artifact. Full write-up in the SIO-1381 closing comment (2026-08-06) and SIO-1405's description.

The judge-strength audit (same comment) is independent corroboration: gpt-4o graded the same impoverished inputs even lower (elastic 0.000) — a stricter judge can't fix an empty input.

## Where the bodies are buried

**1. The serializer — `packages/agent/src/eval/subagent-reports.ts:29-46`** (whole file is ~46 lines; read it). The header comment at lines 4-9 contains the original mistaken premise:

```ts
// SIO-1374: DataSourceResult has no plain-text report field -- only the typed per-datasource
// *Findings objects (kafkaFindings, elasticFindings, etc.) and opaque toolOutputs[].rawJson. The
// per-sub-agent judge grades the serialized *Findings object as that datasource's "report": ...
```

That premise is **wrong**: `DataSourceResult.data` IS the plain-text report (see 3). The loop then serializes only `result[FINDINGS_FIELD_BY_DATASOURCE[result.dataSourceId]]` (lines 31-40), so any datasource whose evidence flowed through non-typed-finding tools serializes as `{}` or is absent.

**2. Why typed findings are usually near-empty** — `extractFindings` (SIO-764) populates `*Findings` from the `TYPED_FINDING_TOOLS` subset only (SIO-1159). Generic `elasticsearch_search` / `esql_query` / `multi_search` — the bulk of elastic's real investigative surface (18+4+1 of DEVOPS-1376's 26 calls) — never lands in typed findings; it reaches the aggregator via the sub-agent's narrative and persisted `toolOutputs[].rawJson` instead.

**3. The overlooked report field — `packages/shared/src/agent-state.ts:447-474`**: `DataSourceResultSchema.data` is `z.unknown()`, but at runtime it is a **string**: `SubAgentOutcome.data` (`packages/agent/src/sub-agent.ts:93-97`) — the sub-agent's own final narrative answer, or the evidence-grounded synthesis when the model returned no narrative (sub-agent.ts:197, `SYNTHESIS_NOTE`/`TRUNCATED_SYNTHESIS_NOTE` at 88-91). This is exactly "what the sub-agent produced, uninfluenced by the aggregator" — the thing the per-sub-agent judge was designed to grade.

**4. The judge that consumes it — `packages/agent/src/eval/evaluators.ts`**: `judgeSubagentReports` batches per-datasource `report` vs `referenceFindings` into one OpenAI call; a datasource absent from `subagentReports` is judged against the placeholder `"(no findings produced by the sub-agent for this datasource)"`. Per-datasource input is already capped by `truncateForJudge` (8,000 chars, explicit marker) — the cap infrastructure the fix needs already exists.

**5. The call site — `packages/agent/src/eval/run-function.ts`**: `buildSubagentReports(finalState.dataSourceResults ?? [])` inside `runAgent`, and the result is embedded in the frozen output store (see the trap in Risks).

## The fix (step-by-step)

**Step 1 — `packages/agent/src/eval/subagent-reports.ts`**: rewrite the loop to serialize the narrative FIRST, typed findings as a labeled supplement; correct the stale header comment. Sketch:

```ts
export function buildSubagentReports(results: DataSourceResult[]): { [dataSourceId: string]: string } {
	const byDatasource = new Map<string, string[]>();
	for (const result of results) {
		const parts: string[] = [];
		// SIO-1405: the sub-agent's own narrative report (SubAgentOutcome.data, a string at
		// runtime; z.unknown() in the schema) is the primary evidence surface. Typed findings
		// alone cover only the TYPED_FINDING_TOOLS subset and serialized {} for most real
		// elastic investigations (DEVOPS-1376: ground truth present 50x in recorded tool
		// results, judge handed {}).
		if (typeof result.data === "string" && result.data.trim().length > 0) {
			parts.push(result.data);
		}
		const field = FINDINGS_FIELD_BY_DATASOURCE[result.dataSourceId];
		const findings = field ? result[field] : undefined;
		if (findings != null) {
			parts.push(`Typed findings: ${JSON.stringify(findings)}`);
		}
		if (parts.length === 0) continue; // absent key, not a misleadingly present empty one
		const existing = byDatasource.get(result.dataSourceId) ?? [];
		existing.push(parts.join("\n"));
		byDatasource.set(result.dataSourceId, existing);
	}
	const report: { [dataSourceId: string]: string } = {};
	for (const [dataSourceId, parts] of byDatasource) {
		report[dataSourceId] = parts.join("\n");
	}
	return report;
}
```

Decisions already made (keep unless you find a reason not to): keep the multi-deployment join; keep absent-key semantics; include `data` even for `status: "error"` results (it is still what the sub-agent produced — the judge grades against ground truth); `FINDINGS_FIELD_BY_DATASOURCE` no longer gates whether a datasource appears (a konnect-like datasource with narrative but no typed-findings mapping now serializes its narrative — correct, and harmless because the judge only asks about `Object.keys(referenceFindings)`).

**Step 2 — `packages/agent/src/eval/subagent-reports.test.ts`**: existing tests pin typed-findings-only behavior — update them, and add: (a) a string `data` is serialized; (b) `data` + typed findings combine with the `Typed findings:` label; (c) non-string `data` (the SIO-640-era `data: null` path, sub-agent.ts:1938) is ignored; (d) whitespace-only `data` yields an absent key; (e) multi-deployment entries still join.

**Step 3 — doc touch**: `packages/agent/src/eval/README.md` mentions `subagent_accuracy_*` grading "raw serialized sub-agent findings" — update the wording to "the sub-agent's report (narrative + typed findings)". Also fix the stale premise comment quoted in Bodies #1.

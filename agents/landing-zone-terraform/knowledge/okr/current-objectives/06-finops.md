# 6. FinOps

*(LZ KB: Tagging strategy · Budgets & guardrails · Cost allocation)*

```
Category: FinOps
Status:   TO BE REVIEWED (LZ KB) / 1 of 9 ADRs Accepted, live 2026-07-31
Owner:    CCoE Platform Team
```

## Objective

Every dollar of spend is attributable to an owner, a cost center, and a business unit — with untagged spend treated as a cost, not a mystery.

## Key Results

- [ ] **KR1 —** 100% of resources carry the 10 mandatory tags generated by `aws_tagging`: `ApplicationName`, `Owner`, `CostCenter`, `BlueprintID`, `BusinessUnit`, `DataClassification`, `BusinessCriticality`, `Environment`, `ManagedBy`, `Approver` — 0 untagged resources (untagged = the team's own uncharged cost, per the FinOps ADR, which is itself the enforcement mechanism).
- [ ] **KR2 —** `DataClassification` and `BusinessCriticality` are drawn from one published, current enum — **currently not true**, see conflict below.
- [ ] **KR3 —** `ManagedBy` has one agreed meaning across every source that documents it — **currently not true**, see conflict below.
- [ ] **KR4 —** Every account budget has a guardrail action (not just an alert) wired to at least one automated response (e.g. notify + tag-based spend cap).

## ⚠ Conflict 1 — `DataClassification` / `BusinessCriticality` enums don't match

| Source | `DataClassification` | `BusinessCriticality` |
|---|---|---|
| AGENT_PROMPT §8 | `Public \| Internal \| Confidential \| Restricted` | `low \| medium \| high \| BusinessCritical` |
| LZ KB FinOps table (published, current standard page) | `Internal · Confidential · Highly Confidential` (no `Public`, no `Restricted`; adds `Highly Confidential`) | `business_operational · BusinessCritical` (lowercase-snake **and** PascalCase shown side by side) |
| Real account YAML (`edp.yml`, per Three-Way Validation) | uses `Highly Confidential` | uses `business_critical` |

This means the "outlier" flagged in the existing Three-Way Validation doc (`edp.yml` using values "outside the documented list") is actually consistent with the **live KB page** — it's AGENT_PROMPT/the Guide's enum that's stale, not the account data. **Recommended fix:** update AGENT_PROMPT §8 to `Public | Internal | Confidential | Highly Confidential` (drop or clarify `Restricted`, confirm with the platform team whether it's still used anywhere) and pick one casing convention for `BusinessCriticality`. Full detail in the [findings note](findings/lzkb-fourth-source-cross-validation.md#extended-conflict-dataclassification--businesscriticality-enums).

## ⚠ Conflict 2 — `ManagedBy` (new finding, now confirmed in real data)

AGENT_PROMPT §8 states `ManagedBy` is "always `Terraform`" (an automation-provenance tag). The LZ KB FinOps table lists `ManagedBy`'s example value as `platform-team@pvh.com` — "Platform management contact," i.e. a **person/team contact**, not a tool-provenance marker. These are two different purposes wearing the same key name. **Confirmed directly in the real account YAML now, not just the KB table:** `aws-lz-account-creator/accounts/edp.yml`'s `common:` block sets `managed_by: eda_owner@pvh.com` — a person's email, exactly matching the KB's reading and contradicting AGENT_PROMPT's "always Terraform." The live account data agrees with the KB, not the prompt. See the [findings note](findings/lzkb-fourth-source-cross-validation.md#new-conflict--managedby-tag-has-two-incompatible-meanings) for the full writeup and recommended fix.

**Correcting a likely assumption:** `ADR-0032` is **"MAP Program"** (AWS Migration Acceleration Program cost-recovery mechanics), *not* "Terraform State Management Strategy" — that's `ADR-0009`, filed under `cap-platform` and governing [Toolbox](07-toolbox.md) instead. If older notes or memory cite ADR-0032 for the state-backend conversation, that's a stale/incorrect cross-reference — don't carry it forward.

**Duplicate ADR number, second instance:** `ADR-0055` is used for two live, unrelated pages — "Mailing" (Workload Enablement, stub, October 2025) and **"CID as FinOps Tool"** (FinOps, created 2026-07-31 — today — as the explicit successor to ADR-0025 above). Neither page carries the formal `cap-finops`/`cap-workload` label consistently yet, which is why the CQL query above returns 9, not 11 — both this and its sibling collision on `ADR-0054` ("Bastion" vs. **"FinOps Governance Model"**, also newly created 2026-07-27, also FinOps-relevant, also not yet labeled) are recent enough that the labeling hasn't caught up. Flag both to the CCoE Platform Team rather than guessing which page "wins" the number.

Read: the only Accepted FinOps decision is Tagging itself (ADR-0013) — which is also the enforcement mechanism KR1 above depends on. Everything about *what to do with the cost data once it's tagged* (budgets, savings plans, power scheduling, the MAP program, and the brand-new CID/FinOps-governance pair) is still Review/Proposal, and two of those newest pages aren't even fully labeled yet. That's consistent with FinOps being an active, fast-moving area right now rather than a stalled one.

## Real-World Examples (from `aws-lz-account-creator` and `aws-lz-finops`, live repos, 2026-07-31)

**Budgets — confirms KR1, and shows KR4 is genuinely not met yet.** `modules/account-bootstrap/budgets.tf`'s `aws_budgets_budget` carries `prevent_destroy = true` and three notification tiers — 80% actual, 100% actual, 90% forecasted — each fanning out to a wider contact list as severity increases. But every one of the three `notification` blocks only sends email; there is no `notification_type` wired to an automated response (no Lambda, no SCP-based spend cap, no automatic stop-action). That's a direct, real-code confirmation that KR4 ("a guardrail action, not just an alert") is aspirational today, not close-but-unverified.

**Undocumented tags, found in real account YAML, not in AGENT_PROMPT's 10-tag list:**
- `map-migrated: mig6ZHOPC45Z1` (in `accounts/edp.yml`'s `common:` block) — an AWS Migration Acceleration Program tracking ID, tied to `ADR-0032` MAP Program above. If MAP cost-recovery becomes Accepted, this tag likely needs to graduate from "appears in some account YAMLs" to a documented 11th mandatory tag.
- `BackupStrategy` (referenced throughout `modules/account-bootstrap/backup.tf`, values `auto | local | default | mission_critical | business_critical | nonprod`) — drives which AWS Backup plan/vault a resource lands in via tag-based `aws_backup_selection` conditions. Not in AGENT_PROMPT §8's tag list at all, despite being load-bearing for backup tier routing (see [Uncovered Domains → Disaster Recovery](08-uncovered-domains.md#disaster-recovery-cap-dr--4-adrs-0-accepted)).

**`business_criticality` casing — both forms are live in the same repo, same day.** `accounts/edp.yml` uses lowercase-snake `business_critical`; `accounts/infra-network.yml` uses PascalCase `BusinessCritical` for the equivalent field. This isn't a historical drift — it's the current, inconsistent, real state of the data, matching the KB table's "both casings shown as legitimate" framing exactly (see Conflict 1 above).

**Code shipped ahead of its own ADR.** The `aws-lz-finops` repo (created 2026-07-22) already implements Cost Intelligence Dashboards — CUDOS v5, the FOCUS/CUR2 Glue catalog, and CloudFormation-deployed QuickSight dashboards — via `cid_dashboards.tf` and friends. `ADR-0055` "CID as FinOps Tool," the ADR that's supposed to govern this exact capability, wasn't opened until 2026-07-31 — nine days *after* the implementing repo existed, and it's still Proposal. Terraform shipped before the ADR did. Not necessarily wrong (a working prototype can inform the ADR it's write up for), but worth flagging as a live example of implementation outrunning governance, relevant to AGENT_PROMPT's MCP-mandatory / ADR-policy expectations in [Strategy](01-strategy.md).

## Repository refresh (2026-09-21)

CID is now a cross-repository capability. `aws-lz-finops` added advanced and Tier 3 dashboards, Compute Optimizer, centralized data-collection StackSets, QuickSight folder sharing, and Identity Center-derived row-level security. `aws-lz-monitoring` supplies the corresponding organizational collection permissions and exports, while `aws-lz-account-creator` supplies member-account access. The feature gates in `aws-lz-finops/_variables.tf` are operational dependencies: dashboards must not be enabled before their source collection has produced data. See the [repository refresh](findings/repository-refresh-2026-09-21.md#monitoring-and-finops).
